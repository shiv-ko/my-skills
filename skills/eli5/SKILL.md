# ELI5 HTML図解を作る

対象を初めて知る人が、スクロールするだけで核心をつかめるHTMLを作る。説明を薄くするのではなく、理解に必要な順番へほどく。

## 入力を解釈する

`/eli5 <説明してほしいこと>`の`<説明してほしいこと>`を対象として扱う。読者には前提知識がないと仮定する。解釈によって説明が大きく変わる曖昧さがある場合だけ、短い質問を1つする。それ以外は一般的な意味を採用して進める。

## 説明を設計する

1. 読者が最後に理解すべき核心を、一文で決める。
2. 身近なたとえを1つ選ぶ。
3. 理解に必要な流れを3〜5段階に分ける。
4. 専門用語は最小限にし、「普通の言葉 → 用語」の順で一度だけ紹介する。
5. たとえと実際の仕組みを混同させない。「たとえると」と「実際は」を明示する。

正確さを保つために必要なら周辺情報を調べる。ただし、背景説明を増やすより、核心を理解するために必要な事実を優先する。

## HTMLを作る

単一の自己完結型HTMLファイルとして出力する。CSSと必要最小限のJavaScriptはHTML内へ埋め込み、外部ライブラリ、外部フォント、外部画像、CDNへ依存しない。

ページは次の順にする:

1. 大きなタイトルと「ひとことで」
2. 身近なたとえの大きな図
3. 仕組みを3〜5枚の図で順番に説明
4. 「つまり」で核心をもう一度示す

## 見た目の基準

- 図を主役にし、文章で余白を埋めない。
- HTML/CSSの図形またはinline SVGを使う。ASCII図は使わない。
- 1画面につき1つの考えだけを見せる。
- 見出しは短く、ラベルは数語、本文は1〜2文に抑える。
- 大きな文字、十分な余白、高いコントラストを使う。
- 色だけで意味を区別せず、形やラベルも併用する。
- スマートフォンでも横スクロールや文字切れが起きないようにする。
- 動きは理解を助ける場合だけ使い、`prefers-reduced-motion`を尊重する。

## 分かりやすさの基準

- 最初から略語や専門用語を並べない。
- 一度に複数の例を出さない。
- 例やたとえを、事実そのものとして断定しない。
- 重要な例外がある場合は、最後に短い注意書きとして示す。
- 「簡単に言うと」と宣言するだけで、難しい説明を続けない。
- 読者が図だけを追っても、話の順番を理解できるようにする。

## 保存して検証する

ユーザーが保存先を指定していない場合は、現在のコードリポジトリ外にあるユーザー向け成果物の場所へ保存する。安全な英語slugを含む`.html`ファイル名にする。

保存後にHTMLをブラウザまたはレンダリング手段で確認し、次を検証する:

- ファイル単体で開ける
- 外部通信なしで図と文字が表示される
- デスクトップとスマートフォン幅で内容が切れない
- 図の順番とラベルだけで核心を追える
- 誤字、重なり、低コントラスト、不要な長文がない

最後に、完成したHTMLへのリンクと、何を説明したものかを一文だけ返す。

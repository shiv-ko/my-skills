# Agent Skillsを統合する

Gitリポジトリを信頼できる正本にし、実行環境のSkillディレクトリを導入先として扱う。名前は英語のまま、説明と手順は日本語にし、元の挙動とライセンスを保持する。

## 原則

- 書き込み前に、対象範囲を読み取り専用で棚卸しする。
- 更新日時だけで正本を決めない。既存のGit管理版、ユーザーの方針、内容差分、上流の出典を確認する。
- 元コピー、ユーザーの未コミット変更、製品固有設定を勝手に削除・上書きしない。
- npxキャッシュやCLI本体と、実際の`SKILL.md`を含むSkillを区別する。
- 公開、push、リポジトリ作成は、ユーザーが明示的に求めた範囲でのみ行う。
- シークレット、個人パス、アカウント情報を公開用リポジトリへ入れない。

## 1. スコープと保存先を解決する

リポジトリルート、現在の作業ディレクトリ、Codexホーム、Claude設定ディレクトリ、プロジェクトスコープの有無を確認する。環境変数や製品バージョンで保存先が変わるため、パスを決め打ちしない。

候補は、ユーザーが指定した範囲に限定して調べる:

- Codex: `$CODEX_HOME/skills`、`~/.codex/skills`、`~/.agents/skills`、`.agents/skills`
- Claude Code: `$CLAUDE_CONFIG_DIR/skills`、`~/.claude/skills`、`.claude/skills`
- 他ツール: `.agent/skills`、OpenSkillsのメタデータ、既知のnpxインストール先

ホーム全体を無制限に再帰探索しない。公式の保存先や挙動が作業結果に影響する場合は、その時点の公式ドキュメントを確認する。

## 2. 読み取り専用で棚卸しする

各Skillについて、名前、絶対パス、スコープ、実体かシンボリックリンクか、出典、ライセンス、同梱リソース、Git管理状況を記録する。`.openskills.json`などの由来情報があれば、上流URL・subpath・commitの確認材料として使う。

結果は次に分類する:

- `unique`: 正本へ未収録のSkill
- `duplicate-identical`: 意味もリソースも同一
- `duplicate-diverged`: 同名だが内容が異なる
- `convertible`: 製品固有表現を分離すれば移植可能
- `non-skill`: npxキャッシュ、CLI、MCPサーバーなどSkillではないもの
- `blocked`: 出典、所有権、ライセンス、競合が解決できないもの

棚卸し表と判定基準には[監査チェックリスト](references/audit-checklist.md)を使う。

## 3. 正本と競合方針を決める

既存のGitリポジトリがある場合は原則として正本にする。重複コピーが古い、または製品向けに劣化しているだけなら、正本を維持して上書きしない。同名の両方に実質的な編集がある場合は、意味上の差分を示してユーザーに選択を求める。

作業ツリーがdirtyなら、既存変更を列挙して保持し、今回の変更と重なる場合だけ停止する。コミットは今回追加・更新したパスだけを対象にする。

## 4. Skillを取り込み、日本語版へ変換する

上流または導入済みコピーから、`SKILL.md`と参照される`references/`、`scripts/`、`assets/`を相対パスを保って取り込む。

- ディレクトリ名とfrontmatterの`name`は英語のkebab-caseを維持する。
- `description`と本文を日本語にし、トリガー条件、必須工程、例外、禁止事項、コマンドの意味を落とさない。
- コード、コマンド、オプション、識別子、パス、ファイル名は、互換化に必要な場合を除いて翻訳しない。
- ポータブルなfrontmatterは`name`と`description`だけにする。
- Claude専用フィールドはそのままCodexへコピーせず、必要な挙動を本文へ移すか、製品固有アダプタとして保持する。
- Codex用`agents/openai.yaml`には、日本語の表示名、短い説明、`$skill-name`を含む既定プロンプトを生成する。
- 完全同等に表現できない機能は隠さず、差分と代替手段を記録する。

## 5. 出典とライセンスを保持する

上流のLICENSE、著作権表示、NOTICEを確認し、要求されるファイルをSkill内に保持する。READMEなどの管理表に上流リポジトリ、基準commit、変更内容を記録する。

Skill単体のライセンスをリポジトリ全体へ自動適用しない。ライセンス不明、再配布禁止、著作権表示の欠落がある場合は、public公開を`blocked`として止める。法的判断が必要な点は断定せずユーザーへ示す。

## 6. 検証する

次を確認し、失敗した項目を直してから導入する:

1. Skill構造とYAML frontmatterを公式validatorで検証する。
2. `SKILL.md`から参照される相対リンクと同梱ファイルの存在を確認する。
3. 名前の重複、壊れたシンボリックリンク、個人の絶対パス、シークレットらしき値を確認する。
4. 追加スクリプトは代表的な入力で実行する。
5. 大容量ダウンロード、外部書き込み、認証を伴う検証は、必要性を説明して許可を得る。
6. 原典との差分が、翻訳・互換化・メタデータ追加・軽微な整形だけであることを確認する。

## 7. Gitへ統合して導入する

管理表とインストーラーがある場合は新しいSkillを認識させる。差分、検証結果、ライセンス表記を確認し、今回の変更だけをコミットする。remoteが未設定ならローカルコミットで止める。

正本から、現在のCodexが実際に参照するSkillディレクトリへ導入する。同名の既存Skillを更新する場合は復元可能な方法を使う。複数の探索先へ同名Skillを重複配置しない。導入後は正本と導入先を比較し、同期状態を確認する。

## 8. 結果を報告する

次を簡潔に報告する:

- 正本の場所と導入先
- 追加、維持、競合、スキップ、非Skillと判定した項目
- 日本語化・互換化で生じた差分
- 保持したライセンスと出典
- 実施した検証
- コミットIDとremote/pushの状態
- 残っているユーザー変更や未解決事項

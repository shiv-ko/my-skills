# 学習ロードマップを作る

学習者が「次に何を学ぶか」「説明できるようになったか」「実例とどうつながるか」を追えるObsidianノートを作る。ロードマップは学習中にAIから説明を受け、本人がメモを書き足すための地図であり、最初から教科書の本文を埋め尽くさない。マスターに資料・演習・進捗を集め、番号付きページは要点とAIへの質問をたどる入口にする。

## 入力と保存先

- 入力が単語だけなら、まず意味の範囲・代表的な利用場面・前提知識を調べ、妥当な学習目標を仮置きする。入力が文章なら、その文章から目的、対象範囲、既知の知識、実例、制約を抽出する。ユーザーの文章にある技術的な主張も必要に応じて検証する。
- 対象のObsidian Vaultと保存場所が分かる場合はそこに作る。既存の関連ノートを確認し、使えるものはリンクする。同名ファイルは内容を確認し、ユーザーのメモや進捗を消さない。
- Vaultが特定できない場合は、書き込み可能な成果物ディレクトリにObsidian互換のMarkdownを作り、移動先をユーザーに案内する。保存先を勝手に推測しない。
- 学習期間、現在の水準、最終成果物が重要で不明なら簡潔に尋ねる。回答を待つ間も調査を進め、任意の設定なら仮定を明記して作る。週数や学習時間を根拠なく固定しない。

## 調査と設計

1. 目標から逆算し、到達に必要な概念・操作・実践・判断を洗い出す。前提関係を確認し、抽象概念から実例へ進む順序を決める。独立した項目は無理に一列へ並べない。
2. 各段階の中心概念と、学ぶための参考サイトを実際に調べる。公式文書、標準仕様、教育機関、一次資料を優先し、分かりやすい解説は補助に使う。版、公開日、対象読者、閲覧可能性を確認する。リンク先を確認できない資料を、読める資料として勧めない。
3. 参考資料は段階に対応付け、何を読むための資料かを一言添える。検索結果のURLや架空の書誌情報で埋めない。対立する説明や更新されやすい内容は、確認日と未確定の点を示す。
4. 各段階で「答える問い」「学ぶ概念」「手を動かすこと」「本人が残すメモ」「説明できたかを判定する問い」を設計し、マスターに簡潔にまとめる。実践対象がないテーマなら、比較、図解、例への適用など適切な課題に替える。
5. 完了条件は観察できる行動で書く。「理解する」だけで終わらせず、自分の言葉で説明する、比較する、図示する、未知の例へ適用するなどで判定する。

## Obsidianノートの形

- ロードマップごとにフォルダを作り、その中にマスターノートと番号付きの個別ノートを置く。マスターには、役割、最終目標、学習順序、進捗表、全体の完了条件、各段階の概要・演習・理解チェック・参考資料・学習ログを入れる。前提関係が見やすくなる場合はMermaid図を使う。段階数と期間はテーマに合わせる。
- マスターから各番号付きノートへ `[[個別ノート名]]` でリンクする。番号付きノートの初期内容は、タイトル、`要点を追う見出し`（小見出しのみ）、`AIに聞く質問`（箇条書き）のみとする。学習目的の説明、参考資料、演習、理解チェック、メモ欄は追加せず、マスターに置く。既存の概念ノートへのリンクもマスターにまとめ、存在しないノートへのリンクを大量に残さない。既存の個別ノートに本人の追記がある場合は削除しない。
- マスターにYAMLフロントマターを使う場合は有効な構文にする。タイトル、aliases、tags、status、created、updatedなどは必要なものだけ入れ、リストの字下げを確認する。番号付きノートには、初期内容を絞るためフロントマターを付けない。
- 進捗状態の意味を明示し、初期状態を実際の学習状況に合わせる。ユーザーの説明や観察を確かめずに「説明できる」「実装で確認済み」へ進めない。
- ユーザー固有のコードや環境が与えられていれば、一般概念と実例を対応付ける表を加える。未確認の実装・設定は空欄または「未確認」とし、推測を事実として書かない。
- 保存後、全ての `[[リンク]]` が作成したノートまたは既存ノートを指すこと、外部リンクが実在すること、進捗と完了条件が矛盾しないことを確認する。

## 学習を進めるとき

ロードマップや個別ノートの説明を頼まれたら、現在の段階と本人のメモを読み、前提から短い単位で説明する。具体例を示し、理解チェックの問いで確かめる。分からなかった点はマスターの学習ログに残せる形で整理する。進捗を更新する際は、本人が説明・実践した根拠を記録し、次に学ぶ一項目を示す。既存の本人の記述は勝手に書き換えない。

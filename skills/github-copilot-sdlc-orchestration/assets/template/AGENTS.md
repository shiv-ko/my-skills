# Agent instructions

## 適用範囲

このファイルはリポジトリ全体に適用する。作業対象により近い`AGENTS.md`やpath-specific instructionsがあれば、その領域固有の指示も読む。指示が矛盾する場合は、勝手に解釈せずユーザーへ確認する。

## 作業原則

- 依頼と受け入れ条件を満たす最小の変更に限定する。
- 既存の設計、命名、依存関係、テスト方式を先に調べ、正当な理由なく新しい方式を持ち込まない。
- 作業開始時点の未コミット変更はユーザーのものとして扱い、上書き、破棄、巻き戻しをしない。
- 生成物、lockfile、migration、公開APIを変更するときは影響範囲を明示する。
- 秘密情報、個人情報、tokenをログ、成果物、commitへ含めない。

## 工程間の成果物

対象ごとに`docs/development/issues/<task-id>/`を作業記録の正本とする。Issue番号がなければ、衝突しない短いtask-idを使う。

```text
requirements.md             要件、受け入れ条件、未決事項
plan.md                     変更計画、対象ファイル、検証方法
plan-review.md              計画レビュー結果
test-evidence.md            テスト設計とRED/validationの証拠
implementation-evidence.md  実装内容と検証結果
review.md                   独立コードレビュー結果
pr-artifacts.md             PRタイトル・本文案と最終チェック
```

成果物には、結論だけでなく参照したファイル、実行したコマンド、観測した結果を残す。前工程の成果物と実際のコードが矛盾する場合は、後工程で都合よく修正せず差し戻す。

## テストと実装の境界

- test担当は受け入れ条件を検証するテストまたは検証手順を作り、プロダクションコードを変更しない。
- implement担当は原則としてテストを変更しない。テストが誤っている疑いがあれば、根拠を示してtest担当へ戻す。
- snapshot更新、assertion削除、skip追加、例外の握りつぶしによって失敗を消さない。
- 新規テストを作ること自体を目的にしない。既存テストで十分な変更は、対象検証の実行結果を残す。

## 検証

- 正しいコマンドはREADME、package manifest、task runner、CI設定から確認する。推測したコマンドを正本へ書かない。
- 変更箇所に近い検証から実行し、最後に影響範囲に応じたtest、lint、typecheck、buildを行う。
- 未実行の検証と理由を明記する。実行していない検証を成功扱いしない。

## 停止と承認

次の場合は自動進行を止める。

- 受け入れ条件または設計判断が曖昧で、選択により挙動や公開契約が変わる。
- 意図した理由で失敗するテストを作れない、または既存仕様と要件が矛盾する。
- test、build、lint、typecheckが失敗している。
- `[blocker]`が未解消である。
- データ損失、権限変更、互換性破壊、課金、外部公開を伴う可能性がある。

`git push`、Issue・PR作成、merge、release、deployなど共有環境を変更する操作は、対象と内容を示してユーザーの明示的な承認を得てから行う。

# 差分をMarkdownで説明する

指定されたコード変更について、充実した読みやすい解説を作成する。

次のセクションを含める。

- 背景: この変更に関係する既存システムを説明する。このために周辺コードを広く調査する。読み手がどの程度の前提知識を持つか分からないため、初心者向けの詳しい背景説明を含める。その部分は、すでに詳しい読者なら読み飛ばせるようにする。その後、変更に直接関係する、より焦点を絞った背景を説明する。
- 直感: コード変更の核となる直感を説明する。詳細をすべて説明するのではなく、本質を伝えることに重点を置く。簡単なサンプルデータを使った具体例を示す。図やダイアグラムを積極的に使う。
- コード: コードへの変更を大まかに案内する。理解しやすい単位と順序で変更をまとめる。
- クイズ: このPRに関する読み手の理解を確認する問題を5問作成する。難易度は中程度とし、PRの本質を実際に理解しなければ答えられない程度にする。ただし、ひっかけ問題にはしない。読み手が本当に理解できたかを自分で確認できるようにすることが目的である。選択式問題として提示し、各問題の直後に折りたたまれた正解とフィードバックを置く。

## 形式

- 自己完結型のMarkdownファイルを1つ出力する。セクション見出しとリンク付き目次を備えた縦長の文書にする。最上位の構造にタブを使用しない。画像などの外部ファイルがなくても内容を理解できるようにする。
- ファイルはコードリポジトリ外にあるPC上の共通的な場所へ保存する。ファイルを時系列で並べやすく、バージョン管理の対象外に保てるよう、ファイル名は必ず当日の日付を`YYYY-MM-DD-`形式で先頭に付ける。例: `/tmp/2026-01-12-explanation-<slug>.md`
- Martin Kleppmannの文章のように、明快で流れがよく、読者を引き込む古典的な文体で書く。セクション間を滑らかにつなぐ。
- ダイアグラムにはMermaidを優先する。説明全体で再利用できる少数の図式ファミリーを選び、さまざまなケースの説明に使う。有用なダイアグラムの例:
  - UI変更を説明するための、ユーザーがアプリで目にするUIを大幅に簡略化したフローチャート。
  - コンポーネント間のデータフローまたは通信を示すシステム図。この図には必ずサンプルデータを含める。
- ASCIIアートのダイアグラムを使用しない。Mermaidで表現しにくい場合は、Markdownの表、リスト、短い段階的な説明を使用する。
- コードブロックには言語名付きのMarkdownコードフェンスを使用する。ファイルを保存する前に、すべてのコードフェンスが正しく閉じられ、本文や後続セクションを誤ってコードブロックへ取り込んでいないことを確認する。
- 重要な概念や定義、注意すべきエッジケースなどには、引用ブロックまたはGitHub Flavored Markdownのアラートを使う。
- 各クイズの正解と解説は`<details><summary>回答を見る</summary>...</details>`で折りたたみ、読み手が自分で回答してから開けるようにする。正解だけでなく、各選択肢が正しいまたは誤っている理由を説明する。
